## 1. 작업 목표

Step 30까지 구현된 주소 기반 생성형 코스 기능을 기준으로, 다음 단계에서 필요한 보안 안정화와 UX 고도화 방향을 문서로 정리했다.

이번 Step은 코드 구현이 아니라 후속 작업 추적을 위한 문서화 Step이다. `plan`, `step`, `pr` 번호를 모두 31번으로 맞춰 이후 작업자가 같은 기준으로 이어서 볼 수 있게 했다.

## 2. 정리한 배경

사용자 피드백과 코드 점검 결과, RWR의 다음 개선 방향은 크게 두 갈래로 나뉜다.

첫 번째는 보안과 운영 안정성이다. 생성형 코스는 ORS와 Kakao Local 같은 외부 API에 의존하므로, 요청 제한, timeout, 짧은 캐싱, 로그 민감정보 축소가 필요하다.

두 번째는 실제 사용자가 코스를 이해하고 따라갈 수 있게 만드는 UX 개선이다. 출발지가 어디인지, 겹치는 경로에서 어느 방향으로 가야 하는지, 자동 생성 경로의 거리와 정확도 한계를 어떻게 안내할지가 중요하다.

## 3. 현재 적용된 항목

### 3.1 프론트엔드

- 코스 생성 요청 중 버튼 비활성화가 적용되어 있다.
- 다시 추천 요청 중 버튼 비활성화가 적용되어 있다.
- API 실패 시 사용자에게 에러 메시지를 보여준다.
- 우편번호 서비스 기반 주소 선택과 좌표 변환 실패 안내가 적용되어 있다.
- POI 선호 토글은 최대 2개 선택 제한이 적용되어 있다.

### 3.2 백엔드

- `helmet`이 적용되어 기본 보안 헤더를 설정한다.
- JSON body limit이 적용되어 있다.
- `CORS_ORIGIN` 기반 CORS 허용 도메인 제한이 적용되어 있다.
- 주소, 좌표, 거리, 시간, 운동 유형, POI 선호, 우회 강도 입력 검증이 적용되어 있다.
- ORS 실제 응답 거리를 기준으로 목표 거리 허용 범위를 검증한다.

### 3.3 UX / 기능

- 주소 기반 순환 코스 생성이 가능하다.
- 출발-도착 코스 생성이 가능하다.
- 지도에 출발/도착/방향/중간 번호 마커를 표시한다.
- 결과 화면에서 목표 거리와 실제 추천 거리 차이를 확인할 수 있다.
- POI 선호를 코스 생성 힌트로 사용할 수 있다.

## 4. 후속 보안 과제

### 4.1 P0. API rate limit

아직 `express-rate-limit`은 적용되어 있지 않다.

후속 작업에서는 전체 API 기본 제한과 외부 API 호출 비용이 큰 `/api/routes/*`, `/api/locations/*` 제한을 분리하는 것이 좋다.

새 npm 패키지 추가가 필요하므로 실제 구현 전 사용자 승인이 필요하다.

### 4.2 P0. 외부 API timeout

ORS, Kakao Local 요청에는 timeout이 필요하다.

외부 API가 느리거나 응답하지 않을 때 서버 요청이 오래 유지되지 않도록 `AbortController` 기반 timeout을 적용하는 것이 좋다.

### 4.3 P1. 30초 메모리 캐싱

같은 주소 변환, 같은 POI 검색이 반복될 수 있으므로 짧은 TTL의 서버 메모리 캐시를 검토한다.

권장 우선순위는 아래와 같다.

```text
1. geocode / reverse-geocode
2. POI search
3. ORS route generation은 같은 seed와 같은 요청일 때만 선택 검토
```

### 4.4 P1. 로그 민감정보 축소

서버 로그에는 주소 원문, 좌표, 요청 body 전체, API key가 남지 않도록 해야 한다.

에러 로그는 `method`, `path`, `status`, `errorName` 중심으로 정리하는 것이 좋다.

### 4.5 P1. body limit 기준 정리

현재 기본 body limit은 4kb로, 피드백 기준인 10kb보다 더 엄격하다.

후속 문서에서는 "10kb 이하, 현재 기본 4kb"로 정리하거나, 운영 기준에 맞춰 10kb로 변경할지 결정하면 된다.

## 5. Cloudflare / Nginx 과제

Cloudflare와 Nginx 관련 설정은 코드보다 운영 환경 설정에 가깝다.

후속 작업에서 확인할 항목은 아래와 같다.

- Cloudflare HTTPS 적용
- `/api/routes/*`, `/api/locations/*` 경로 rate limit
- 테스트 환경 Cloudflare Access 보호
- Nginx `client_max_body_size` 설정
- Nginx proxy timeout 명시
- 필요 시 Nginx `limit_req` 보조 적용

Docker 또는 Nginx 설정 변경은 사용자 확인 후 진행해야 한다.

## 6. 후속 UX 과제

### 6.1 P0. 출발지 인지 개선

사용자가 "어디가 출발인지 모르겠다"고 느끼지 않도록 결과 지도와 요약 정보에서 출발지를 더 강하게 보여줘야 한다.

추천 작업:

- 출발 마커 강조
- 출발지 주소를 결과 요약 첫 줄에 노출
- 첫 이동 방향 카드 추가
- 출발/도착 색상 구분 강화

### 6.2 P0. 겹치는 경로 방향 표시 강화

겹치는 구간에서는 현재 방향 마커만으로 부족할 수 있다.

추천 작업:

- 경로 화살표 밀도 개선
- 출발 구간 색상 강조
- 겹치는 구간 offset 표시 검토
- 모바일 zoom 기준 표시 밀도 조절

### 6.3 P0. 정확도 안내와 실패 대응

자동 생성 경로는 실제 도로 상황, 공사, 보행 가능 여부에 따라 달라질 수 있다.

결과 화면에는 이 한계를 명확히 안내하고, 실패 시에는 "다시 시도"뿐 아니라 거리/시간 조정, 다른 주소 선택, POI 선호 끄기 같은 다음 행동을 안내해야 한다.

### 6.4 P1. 거리/시간 선택 UX 보강

현재 직접 설정 range는 있으므로 기본 구조는 있다.

후속으로는 직접 설정 상태를 더 눈에 띄게 하고, 실패 후 바로 목표값을 바꿀 수 있는 재시도 UI를 검토한다.

### 6.5 P1 이후. 경험 확장

후순위 확장 후보는 아래와 같다.

- 중간 지점 직접 선택
- 관광/명소 테마
- POI 기반 주변 정보 요약
- AI 설명 생성 실험
- 경로 색상 커스텀
