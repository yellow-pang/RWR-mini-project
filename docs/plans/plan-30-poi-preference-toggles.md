# Plan 30. POI 선호 토글과 도심지 매칭 보정

## 상태

- 브랜치: `feat/step-30-poi-preference-toggles`
- 단계: 구현 진행
- 기준 문서: `docs/plans/plan-29-poi-waypoints.md`, `docs/steps/step-29-poi-waypoints.md`, `docs/pr/pr-29-poi-waypoints.md`

## 배경

Step 29에서는 코스 분위기를 단일 선택값으로 받아 Kakao Local API의 키워드 검색 결과를 경유지 후보로 사용했다.

현재 확인된 문제는 두 가지다.

1. 서울 같은 도심지에서도 `편의점`, `카페` 같은 POI가 기대보다 잘 매칭되지 않을 수 있다.
2. 코스 조건 선택지가 늘어나면서 홈 화면의 세로 길이가 길어지고, 사용자가 중요한 선택을 빠르게 하기 어렵다.

이번 Step 30의 목표는 POI 검색 정확도를 올리고, 코스 분위기 UI를 단일 선택 목록에서 더 가벼운 토글 방식으로 바꾸는 것이다.

## 핵심 판단

### 1. POI 검색 방식

현재보다 좋은 방식은 `카테고리 검색 우선 + 키워드 검색 fallback`이다.

Kakao Local API는 편의점, 카페처럼 분류가 명확한 장소는 키워드보다 카테고리 검색이 더 안정적일 가능성이 높다. 반대로 공원, 녹지, 산책로처럼 카테고리 코드로 딱 떨어지지 않는 장소는 키워드 검색이 필요하다.

권장 방식:

```text
편의점:
카테고리 검색 CS2 우선
실패 시 키워드 "편의점" fallback

카페:
카테고리 검색 CE7 우선
실패 시 키워드 "카페" fallback

공원/녹지:
키워드 "공원", "녹지" 중심
필요 시 후속 Step에서 검색어 보정
```

### 2. UI 방식

현재 구현은 `코스 분위기`를 하나만 고르는 구조다.

```text
코스 분위기
[아무거나] [공원 위주] [하천/산책로] [카페 근처] [편의점 근처]
```

문제는 선택지가 늘어날수록 홈 화면이 길어지고, 사용자가 반드시 선택해야 하는 것처럼 느낄 수 있다는 점이다.

권장 방향은 기본 추천은 유지하고, 선택적 선호만 토글로 추가하는 방식이다.

```text
코스 분위기
추천 균형 코스

추가로 반영할 요소
[공원/녹지] [카페 근처] [편의점 근처]
```

아무 토글도 켜지 않으면 기존처럼 균형 코스로 추천한다. 사용자가 원하는 분위기가 있을 때만 토글을 켠다.

## UI 선택지

### A안. 항상 보이는 compact 토글

현재 구현에서 가장 적게 바꾸면서 세로 길이를 줄이는 방식이다.

```text
코스 분위기
추천 균형 코스

추가 반영
[공원/녹지] [카페] [편의점]
```

장점:

- 사용자가 기능을 바로 볼 수 있다.
- 기존 단일 선택 UI를 토글 칩으로 바꾸면 되어 구현 부담이 낮다.
- 모바일에서도 세로 길이가 크게 늘지 않는다.

단점:

- 토글이 항상 보이므로 완전히 숨기는 방식보다는 약간의 공간을 쓴다.

추천도: 가장 추천

### B안. 기본/맞춤 분리

기본은 한 줄로 보여주고, `맞춤`을 선택했을 때만 토글을 보여준다.

```text
코스 분위기
[추천 균형] [맞춤]

맞춤 선택 시:
[공원/녹지] [카페] [편의점]
```

장점:

- 기본 사용자는 화면이 가장 짧다.
- POI 선호를 고급 설정처럼 다룰 수 있다.

단점:

- 사용자가 `맞춤`을 눌러야 토글을 발견한다.
- 상태가 하나 더 늘어나 구현과 설명이 조금 복잡해진다.

추천도: 기본 화면을 아주 짧게 만들고 싶으면 추천

### C안. 상세 설정 접기/펼치기

코스 분위기를 고급 설정 안에 넣는다.

```text
코스 분위기
추천 균형 코스

[세부 조정 열기]
```

펼친 뒤:

```text
[공원/녹지] [카페] [편의점]
```

장점:

- 첫 화면이 가장 단순하다.

단점:

- POI 선호 기능이 숨겨져서 사용 빈도가 낮아질 수 있다.
- MVP 단계에서는 인터랙션 대비 효용이 크지 않다.

추천도: 후순위

선택 규칙은 아래처럼 둔다.

```text

추천 균형 코스

1개 선택:
해당 POI 선호 우선 반영

2개 선택:
두 선호를 모두 후보로 검색하되 가까운 후보 우선

3개 선택:
가능은 하지만 검색 호출이 늘어날 수 있으므로 MVP에서는 최대 2개 권장
```

## 사용자가 확인할 사항

### 1. UI 방식

권장: A안

선택 필요:

```text
A. 항상 보이는 compact 토글
B. 기본/맞춤 분리
C. 상세 설정 접기/펼치기
```

### 2. 토글 항목

권장:

```text
공원/녹지
카페 근처
편의점 근처
```

후보:

```text
대중교통 근처
하천/산책로
관광/명소
```

현재는 `하천/산책로`를 기본 토글에서 제외하는 것을 권장한다. 키워드 검색 정확도가 지역마다 크게 다를 수 있어, Step 30에서는 안정적인 항목부터 보정하는 편이 낫다.

### 3. 최대 선택 개수

권장:

```text
최대 2개
```

이유:

- 사용자가 선택하기 쉽다.
- API 호출 수를 제어하기 좋다.
- 여러 선호가 서로 충돌하는 상황을 줄일 수 있다.

### 4. 실패 시 표시 방식

권장:

```text
선택한 분위기 후보가 부족해 균형 코스로 추천했어요.
```

이 문구는 결과 카드나 코스 설명 영역에 작게 표시한다.

## 구현 범위 제안

### 클라이언트

- `routeTheme` 단일 선택 UI를 `poiPreferences` 토글 배열로 변경한다.
- 아무 토글도 선택하지 않으면 서버에 균형 추천 상태로 요청한다.
- 토글은 최대 2개까지만 선택 가능하게 한다.
- 결과 카드에는 선택한 선호와 실제 적용 여부를 간단히 표시한다.

예상 요청 형태:

```json
{
  "routeTheme": "balanced",
  "poiPreferences": ["park", "convenience"]
}
```

기존 `routeTheme`는 바로 제거하지 않고 호환용으로 유지하는 것을 권장한다.

### 서버

- `poiCategories.js`에 선호 항목별 검색 전략을 정의한다.
- `poiService.js`에 Kakao 카테고리 검색을 추가한다.
- 카테고리 검색 결과가 없으면 키워드 검색으로 fallback한다.
- POI 후보는 중복 제거 후 거리순으로 정렬한다.
- 후보가 부족하면 기존 랜덤 경유지 fallback을 그대로 사용한다.

예상 검색 전략:

```js
{
  convenience: {
    categoryCodes: ["CS2"],
    keywords: ["편의점"]
  },
  cafe: {
    categoryCodes: ["CE7"],
    keywords: ["카페"]
  },
  park: {
    categoryCodes: [],
    keywords: ["공원", "녹지"]
  }
}
```

## 구현 기록

2026-06-03 기준으로 추천 결론의 A안을 적용했다.

- 홈 화면의 `코스 분위기`를 단일 선택 카드에서 compact 토글로 변경한다.
- 토글 항목은 `공원/녹지`, `카페 근처`, `편의점 근처` 3개로 시작한다.
- 선택 개수는 최대 2개로 제한한다.
- 클라이언트 요청에는 기존 `routeTheme`을 유지하면서 `poiPreferences` 배열을 추가한다.
- 서버는 `poiPreferences`를 우선 사용하고, 구버전 `routeTheme` 요청도 내부 선호값으로 변환한다.
- Kakao Local 검색은 편의점/카페에서 카테고리 검색을 먼저 시도하고, 결과가 없으면 키워드 검색으로 fallback한다.
- 공원/녹지는 이번 Step에서 키워드 검색 중심으로 유지한다.
