# Plan 18. GPS 기반 랜덤 코스 자동 추천 옵션 기반 구현

> 작성일: 2026.05.31  
> 브랜치: `feat/gps-location-sorting`  
> 이전 완료 상태: [step-17-api-base-url-cors-fix.md](../steps/step-17-api-base-url-cors-fix.md)

---

## 1. 배경

RWR의 MVP는 PostgreSQL에 저장된 코스 중 사용자가 선택한 거리, 소요 시간, 운동 유형에 맞는 코스를 랜덤 추천하는 방식으로 구현되어 있다.

하지만 최종 목표는 단순히 "이미 있는 코스 중 가까운 코스"를 보여주는 것이 아니라, 사용자의 현재 위치를 기준으로 매일 지루하지 않은 걷기/조깅/러닝 코스를 자동으로 추천하는 것이다.

따라서 Step 18은 기존 DB 코스의 가까운 순 정렬을 메인 목표로 삼지 않고, GPS 기반 자동 코스 추천 옵션과 fallback 기반을 먼저 구현한다.

---

## 2. 최종 목표

사용자가 거리, 소요 시간, 운동 유형을 선택하면 브라우저에서 현재 위치를 가져오고, 현재 위치를 출발점으로 하는 랜덤 운동 코스를 자동 추천한다.

```text
현재 위치 + 목표 거리 + 소요 시간 + 운동 유형
→ 랜덤 코스 생성/추천
→ 지도에 경로 표시
→ 실패 시 기존 DB 랜덤 추천 fallback
```

---

## 3. Step 18 목표

이번 단계에서는 실제 외부 라우팅 API 연동까지 한 번에 구현하지 않는다. 대신 GPS 기반 추천 옵션을 UI와 코드 구조에 추가하고, 다음 단계에서 ORS 같은 라우팅 엔진을 붙일 수 있는 기반을 만든다.

### 포함 범위

- Geolocation API로 사용자 현재 위치 취득
- 위치 권한 거부/실패 시 기존 랜덤 추천 fallback
- 추천 방식을 "기존 DB 랜덤 추천"과 "GPS 기반 자동 추천"으로 분리할 구조 추가
- 홈 화면에 GPS 기반 추천 옵션 추가
- GPS 추천 옵션 선택 시 위치 취득 후 기존 DB 랜덤 추천으로 fallback
- 현재 MVP와 최종 목표의 차이를 문서화
- MVP 중심으로 작성된 기존 docs를 점검하고, 최종 목표와 달라진 내용은 삭제하지 않고 변경 사유를 남겨 수정
- Step 19 이후 ORS Round Trip 연동 계획 정리

### 제외 범위

- 이번 단계에서 ORS API 키, `.env`, Docker 설정은 추가하지 않는다.
- 사용자 위치를 서버로 전송하지 않는다.
- 실제 도로망 기반 polyline 생성은 Step 19 이후로 미룬다.
- 기존 DB 코스의 가까운 순 정렬은 메인 기능으로 구현하지 않는다.
- 생성형 GPS 코스를 즐겨찾기/이력 DB에 저장하는 구조는 추가하지 않는다.

---

## 4. 방향성 결정

### 결정 사항

RWR의 장기 방향은 "기존 코스 추천 서비스"가 아니라 "현재 위치 기반 랜덤 운동 코스 생성/추천 서비스"로 잡는다.

기존 DB 코스 추천은 다음 역할로 유지한다.

- 위치 권한 거부 시 fallback
- 외부 라우팅 API 장애 시 fallback
- MVP 데모와 포트폴리오 안정성 확보
- 추천 이력/즐겨찾기 기능의 기준 데이터

### 왜 가까운 기존 코스 정렬을 메인으로 삼지 않는가

- 사용자의 현재 위치 근처 코스를 보여줄 수는 있지만 "매일 새로운 랜덤 코스"라는 핵심 가치와 다르다.
- DB에 미리 등록된 코스 수와 지역 커버리지가 제한된다.
- 최종적으로 자동 경로 생성 기능을 붙일 때 추천 흐름을 다시 바꿔야 한다.

## 5. Step 18 구현 정책

GPS 추천 옵션은 실제 경로 생성 엔진이 붙기 전까지 아래처럼 동작한다.

1. 사용자가 거리, 소요 시간, 운동 유형을 선택한다.
2. 추천 방식에서 "GPS 기반 자동 추천"을 선택한다.
3. 추천 버튼 클릭 시 브라우저 Geolocation API로 현재 위치를 요청한다.
4. 위치 취득 성공 시 현재 위치는 클라이언트 메모리에만 보관하고 서버에는 전송하지 않는다.
5. Step 18에는 ORS 연동이 없으므로 기존 DB 랜덤 추천으로 fallback한다.
6. 결과 화면에는 "현재 위치는 확인했지만 실제 경로 생성은 다음 단계에서 연결되며, 이번 추천은 기존 코스 fallback"이라는 안내를 표시한다.

위치 권한 거부, 위치 취득 실패, 브라우저 미지원도 같은 방식으로 기존 DB 랜덤 추천으로 fallback한다.

## 6. 대안 비교

| 대안                      | 설명                                         | 장점                                    | 단점                                             | 판단                    |
| ------------------------- | -------------------------------------------- | --------------------------------------- | ------------------------------------------------ | ----------------------- |
| 기존 DB 코스 + Haversine  | 코스 시작점까지 직선 거리 계산               | 구현이 쉽고 위치를 서버에 보내지 않음   | 자동 코스 생성이 아니며 DB 커버리지에 갇힘       | fallback 또는 보조 기능 |
| 카카오맵 + ORS Round Trip | 현재 위치 기준 실제 보행/러닝 순환 경로 생성 | 도로망 기반이라 최종 목표에 가장 가까움 | ORS API 키, 쿼터, 장애 대응, 위치 외부 전송 이슈 | 최종 추천 방향          |
| 카카오맵 + Turf.js        | 브라우저에서 수학적으로 랜덤 좌표/선 생성    | 무료, 빠름, 외부 API 없음               | 도로/보행 가능 여부를 보장하지 못함              | 실험/임시 시각화용      |

## 7. 권장 아키텍처

### 추천 엔진 분리

클라이언트에서 추천 흐름을 명확히 분리한다.

```text
recommendByRandomDb(conditions)
recommendByGpsRoute(conditions, userLocation)
fallbackToRandomDb(conditions)
```

Step 18에서는 추천 방식 상태와 위치 취득 유틸을 추가한다. Step 19에서 `recommendByGpsRoute` 내부를 ORS Round Trip API 연동으로 채운다.

### 위치 정보 정책

- 위치 권한 요청은 사용자가 GPS 기반 추천을 선택했을 때만 수행한다.
- Step 18에서는 위치 정보를 서버로 보내지 않는다.
- Step 19에서 ORS를 붙일 경우, 사용자 위치가 ORS 외부 API로 전송된다는 점을 UI/문서에 명확히 안내한다.

### fallback 정책

아래 상황에서는 기존 DB 랜덤 추천으로 전환한다.

- 브라우저가 Geolocation API를 지원하지 않음
- 사용자가 위치 권한을 거부함
- 위치 취득 시간이 초과됨
- GPS 기반 추천 엔진이 아직 연결되지 않음
- 외부 라우팅 API가 실패함

## 9. Step 19 이후 구현 로드맵

### Step 19. ORS Round Trip API 연동

- ORS API 키 관리 방식 결정
- 클라이언트 직접 호출과 서버 프록시 방식 비교
- 현재 위치와 목표 거리로 순환 경로 요청
- 응답 좌표를 카카오맵 polyline으로 표시
- ORS 실패 시 기존 DB 랜덤 추천 fallback

### Step 20. 추천 품질 개선

- 걷기/조깅/러닝별 프로필과 목표 속도 조정
- 소요 시간 기반 목표 거리 보정
- 같은 방향/비슷한 코스 반복 방지
- 코스 길이 오차 허용 범위 정의

### Step 21. 기록/저장 모델 확장

- 생성된 코스를 즐겨찾기/이력에 저장할지 결정
- 저장한다면 DB 스키마 확장 필요
- 위치/경로 좌표 저장 시 개인정보 정책 재검토
