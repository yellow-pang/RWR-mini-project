## 1. 정리 목적

Step 30까지 RWR은 주소 기반 코스 생성, 출발-도착 코스, 목표 거리/시간 보정, POI 선호 토글까지 구현되어 있다.

이번 문서는 사용 피드백과 보안 점검 내용을 바탕으로 다음 고도화 방향을 정리한다. 실제 코드 변경은 포함하지 않고, 후속 Step에서 어떤 순서로 진행하면 좋은지 판단 기준을 남긴다.

## 2. 현재 적용된 항목 요약

### 프론트엔드

- 코스 생성 요청 중 버튼 비활성화가 적용되어 있다.
- 다시 추천 요청 중 버튼 비활성화가 적용되어 있다.
- 주요 API 실패 시 사용자에게 에러 메시지를 보여준다.
- 우편번호 서비스 기반 주소 선택과 좌표 변환 실패 안내가 적용되어 있다.
- POI 선호는 최대 2개까지 선택할 수 있다.

### 백엔드

- `helmet`이 적용되어 기본 보안 헤더를 설정한다.
- `express.json` body limit이 적용되어 있다.
- `CORS_ORIGIN` 기반 CORS 허용 도메인 제한이 적용되어 있다.
- 주소, 좌표, 거리, 시간, 운동 유형, POI 선호, 우회 강도 입력 검증이 적용되어 있다.
- 생성형 코스는 ORS 실제 응답 거리 기준으로 목표 거리 허용 범위를 검증한다.
- POI 후보가 부족하거나 실패해도 기존 랜덤 경유지 방식으로 fallback한다.

### UX / 기능

- 주소 기반 순환 코스 생성이 가능하다.
- 출발-도착 코스 생성이 가능하다.
- 지도에 출발/도착/방향/중간 번호 마커를 표시한다.
- 결과 화면에서 목표 거리, 실제 추천 거리, 예상 시간, 목표와의 차이를 확인할 수 있다.
- 공원/녹지, 카페 근처, 편의점 근처 POI 선호를 코스 생성 힌트로 사용할 수 있다.

## 3. 남은 보안 과제

### P0. API rate limit

현재 `express-rate-limit`은 아직 적용되어 있지 않다.

추천 작업:

- 전체 API 기본 rate limit을 둔다.
- 외부 API 호출 비용이 있는 `/api/routes/*`, `/api/locations/*`는 더 엄격한 limit을 둔다.
- 헬스체크 `/api/health`는 운영 모니터링을 고려해 별도 기준을 둔다.
- 실패 응답은 기존 API 형식에 맞춰 `{ success: false, message }`로 반환한다.

주의:

- 새 npm 패키지 추가가 필요하므로 사용자 승인 후 진행한다.
- Cloudflare rate limit과 Express rate limit이 충돌하지 않도록 기준을 나눈다.

권장 브랜치:

```text
feat/step-32-api-security-hardening
```

### P0. 외부 API timeout

ORS, Kakao Local 요청에 timeout이 없으면 외부 API 지연 시 서버 요청이 오래 붙잡힐 수 있다.

추천 작업:

- ORS 요청에 `AbortController` 기반 timeout을 적용한다.
- Kakao 주소 변환, 좌표 변환, POI 검색 요청에도 timeout을 적용한다.
- timeout 기본값은 환경변수로 조정 가능하게 하되, 기본값은 짧게 둔다.
- timeout 실패 메시지는 사용자에게 기술 용어를 노출하지 않고 재시도 안내로 표현한다.

주의:

- 환경변수 이름 추가 또는 `.env.example` 변경은 사용자 확인 후 진행한다.
- 환경변수를 추가하지 않는다면 코드 기본값만 먼저 둘 수 있다.

### P1. 같은 요청 30초 캐싱

반복 클릭, 같은 주소 재시도, 같은 POI 선호 반복 요청은 외부 API 호출을 늘릴 수 있다.

추천 작업:

- 1차는 서버 메모리 캐시로 시작한다.
- 주소 geocode 결과를 30초 캐싱한다.
- POI 검색 결과를 30초 캐싱한다.
- ORS 생성 결과 캐싱은 seed와 랜덤성을 해칠 수 있으므로 신중히 적용한다.

권장 기준:

```text
geocode/reverse-geocode: 캐싱 추천
POI search: 캐싱 추천
ORS route generation: 같은 seed와 같은 요청일 때만 선택적으로 검토
```

주의:

- 주소 원문을 캐시 key로 직접 오래 보관하지 않는다.
- 캐시 TTL은 짧게 유지하고, 운영 로그에 주소 원문을 남기지 않는다.

### P1. 로그 민감정보 축소

현재 요청 body를 직접 로깅하지는 않지만, 외부 API 에러 메시지나 디버깅 과정에서 주소 원문이 로그에 남을 수 있다.

추천 작업:

- 서버 에러 로그는 `method`, `path`, `status`, `errorName` 중심으로 남긴다.
- 주소, 좌표, API key, 요청 body 전체는 로그에 남기지 않는다.
- 개발 중 필요한 상세 로그는 별도 플래그가 있을 때만 제한적으로 사용한다.

### P1. 요청 body 10kb 기준 정리

현재 서버는 기본 `4kb` 제한을 사용한다. 피드백 기준은 `10kb` 제한이다.

판단:

- 4kb는 10kb보다 엄격하므로 보안 기준에는 부합한다.
- 다만 문서와 운영 기준을 맞추기 위해 `JSON_BODY_LIMIT` 기본값을 유지할지, 10kb로 조정할지 결정해야 한다.

권장:

- 현재 4kb를 유지하고 문서에 "10kb 이하, 현재 기본 4kb"로 명시한다.

## 4. Cloudflare / Nginx 운영 보안 과제

### P0. HTTPS 적용

Cloudflare를 사용한다면 HTTPS는 Cloudflare 대시보드와 DNS 설정에서 우선 적용한다.

추천 작업:

- Cloudflare SSL/TLS 모드를 운영 환경에 맞게 설정한다.
- 가능하면 `Full` 또는 `Full strict`를 목표로 한다.
- HTTP 요청은 HTTPS로 리다이렉트한다.

주의:

- 현재 `nginx.conf`는 `listen 80`과 `/api` 프록시 중심이다.
- 인증서 방식과 Cloudflare 프록시 사용 여부에 따라 Nginx 설정이 달라진다.

### P0. API 경로 rate limit

Cloudflare에서 `/api/routes/*`, `/api/locations/*`에 별도 rate limit을 둔다.

추천 기준:

- `/api/routes/*`: 가장 엄격하게 제한
- `/api/locations/*`: 중간 수준 제한
- `/api/courses`, `/api/favorites`, `/api/history`: 기본 API 제한

주의:

- Express rate limit은 애플리케이션 보호용이다.
- Cloudflare rate limit은 네트워크 앞단 보호용이다.
- 둘 다 사용하는 것이 좋다.

### P1. 테스트 환경 Access 보호

테스트 또는 데모 환경이 공개 도메인에 연결된다면 Cloudflare Access로 보호한다.

추천 작업:

- 테스트 도메인 또는 staging 경로를 Access 정책으로 보호한다.
- 개인 이메일 또는 GitHub 로그인 기반 접근을 허용한다.
- 운영 공개 도메인과 테스트 도메인을 분리한다.

### P1. Nginx 보완

Cloudflare 앞단 보호와 별개로 Nginx에서도 기본 제한을 둘 수 있다.

추천 작업:

- `client_max_body_size`를 설정한다.
- `/api/` 프록시 timeout 값을 명시한다.
- 필요 시 `limit_req` zone을 추가한다.

주의:

- Docker/Nginx 설정 변경은 사용자 확인 후 진행한다.
- Cloudflare를 주 보호 계층으로 사용할 경우 Nginx rate limit은 보조 역할로 둔다.

## 5. UX 고도화 과제

### P0. 출발지 인지 개선

사용 피드백:

```text
어디가 출발인지 모르겠음
```

추천 작업:

- 결과 지도에서 출발 마커를 더 강하게 표시한다.
- 출발지 주소를 지도 위 또는 결과 요약 첫 줄에 명확히 노출한다.
- 출발 직후 첫 이동 방향을 별도 카드로 보여준다.
- 출발/도착 코스에서는 출발지와 도착지 색을 더 명확히 구분한다.

기대 효과:

- 사용자가 실제로 어디서 시작해야 하는지 바로 이해할 수 있다.
- 생성형 코스의 신뢰도가 올라간다.

### P0. 겹치는 경로 방향 표시 강화

사용 피드백:

```text
코스가 겹칠 경우 화살표가 필요
```

현재 Step 25에서 방향 마커가 적용되어 있으나, 겹치는 구간에서는 여전히 헷갈릴 수 있다.

추천 작업:

- 경로 위 방향 화살표를 더 촘촘히 표시한다.
- 출발 구간 색을 더 강하게 유지한다.
- 겹치는 구간은 약간 offset해서 표시하는 방식을 검토한다.
- 모바일 지도에서 마커가 과하게 많아지지 않도록 zoom 기준 표시 밀도를 조절한다.

## 9. 결론

다음 우선순위는 보안 안정화가 가장 높다.

특히 rate limit, 외부 API timeout, 짧은 캐싱은 비용과 안정성에 직접 영향을 준다. 그 다음에는 사용자가 실제로 코스를 따라갈 수 있도록 출발지, 진행 방향, 실패 안내를 강화하는 것이 좋다.

정리하면 후속 작업은 아래 순서가 가장 안정적이다.

```text
1. API 보안 안정화
2. 지도 출발지/방향 UX 개선
3. 실패 대응과 재시도 UX 개선
4. 관광형/AI/색상 커스텀 같은 경험 확장
```
