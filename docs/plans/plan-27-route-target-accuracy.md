# 작업계획서 - Step 27: 추천 목표 거리/시간 정확도 개선

> **상태**: 계획  
> **작성일**: 2026.06.03  
> **브랜치**: `feat/route-target-accuracy`  
> **목적**: 거리, 시간, 운동 유형 조건을 분리하고 ORS 실제 경로 거리/시간을 기준으로 후보를 검증해 사용자가 선택한 목표에 더 가까운 랜덤 코스를 추천한다.  
> **관련 문서**: [step-26-point-to-point-routes.md](../steps/step-26-point-to-point-routes.md) | [pr-26-point-to-point-routes.md](../pr/pr-26-point-to-point-routes.md)

## 1. 작업 배경

현재 RWR은 주소 기반 생성형 코스에서 `순환 코스`와 `출발-도착 코스`를 지원한다. 서버는 ORS 응답의 실제 `summary.distance`, `summary.duration`을 받을 수 있지만, 추천 성공 여부를 사용자가 선택한 목표 거리/시간과 충분히 비교하지 않는다.

그 결과 사용자가 1km를 선택해도 실제 추천 결과가 2km 이상으로 나오거나, 15분 걷기 코스를 기대했는데 실제로는 훨씬 긴 코스가 추천될 수 있다. 거리, 시간, 운동 유형이 동시에 선택되는 구조도 사용자가 무엇을 기준으로 추천받는지 이해하기 어렵게 만든다.

Step 27에서는 랜덤 코스 추천 경험은 유지하되, 사용자의 선택 기준을 `거리 기준`과 `시간 기준`으로 분리하고, 운동 유형별 속도 계산을 적용한다. 또한 ORS가 반환한 실제 경로 거리/시간을 검증해 목표 범위 안에 들어오는 후보만 추천한다.

사용자가 제공한 UX 참고 방향은 "프리셋 칩 + 직접 조절" 방식이다. 모바일에서 많은 버튼을 나열하지 않고, 자주 쓰는 값은 빠르게 선택하게 하며 세밀한 설정은 직접 설정으로 분리한다.

## 2. 목표

- 홈 화면 추천 조건을 `코스 방식`, `추천 기준`, `운동 유형`으로 명확히 분리한다.
- 추천 기준은 `거리 기준`과 `시간 기준` 중 하나만 선택하게 한다.
- 거리 기준 선택 시 목표 거리와 운동 유형에 따른 예상 시간을 계산해 보여준다.
- 시간 기준 선택 시 목표 시간과 운동 유형에 따른 예상 거리를 계산해 보여준다.
- 거리 프리셋은 1차 구현에서 `1km / 2km / 3km / 5km / 직접 설정`으로 제공한다.
- 시간 프리셋은 1차 구현에서 `15분 / 30분 / 45분 / 60분 / 직접 설정`으로 제공한다.
- 직접 설정은 1차 구현에서 슬라이더 또는 숫자 입력 중 기존 UI에 더 잘 맞는 방식으로 구현한다.
- 서버는 여러 랜덤 후보 경로를 생성하고 ORS 실제 거리/시간 기준으로 목표 오차를 검증한다.
- 허용 범위 안에 들어오는 후보가 여러 개이면 목표값과 가장 가까운 후보를 반환한다.
- 허용 범위 안에 들어오는 후보가 없으면 저장 DB 코스를 억지로 추천하지 않고 실패 안내를 반환한다.
- 결과 화면에는 목표값, 실제 추천값, 목표와의 차이를 표시한다.

## 4. 사용자 흐름

### 4.1 거리 기준 추천

1. 사용자가 출발지 또는 출발/도착지를 선택한다.
2. `코스 방식`에서 `순환 코스` 또는 `출발-도착 코스`를 선택한다.
3. `추천 기준`에서 `거리 기준`을 선택한다.
4. `운동 유형`에서 `걷기`, `조깅`, `러닝` 중 하나를 선택한다.
5. 거리 프리셋 또는 직접 설정으로 목표 거리를 선택한다.
6. 클라이언트가 운동 유형 속도로 예상 시간을 계산해 보여준다.
7. `코스 생성`을 누르면 서버가 실제 ORS 경로 거리 기준으로 후보를 검증한다.
8. 조건에 맞는 후보가 있으면 가장 가까운 코스를 보여준다.
9. 조건에 맞는 후보가 없으면 실패 안내를 보여준다.

### 4.2 시간 기준 추천

1. 사용자가 출발지 또는 출발/도착지를 선택한다.
2. `추천 기준`에서 `시간 기준`을 선택한다.
3. `운동 유형`을 선택한다.
4. 시간 프리셋 또는 직접 설정으로 목표 시간을 선택한다.
5. 클라이언트가 운동 유형 속도로 목표 거리를 계산해 보여준다.
6. `코스 생성`을 누르면 서버가 계산된 목표 거리와 ORS 실제 거리/시간 기준으로 후보를 검증한다.
7. 조건에 맞는 후보가 있으면 가장 가까운 코스를 보여준다.
8. 조건에 맞는 후보가 없으면 거리 또는 시간을 조금 늘리도록 안내한다.

## 5. 계산 기준

운동 유형별 기본 속도는 아래 기준을 사용한다.

| 운동 유형 | 내부 값   | 속도  |
| --------- | --------- | ----- |
| 걷기      | `walk`    | 4km/h |
| 조깅      | `jogging` | 7km/h |
| 러닝      | `running` | 9km/h |

시간 기준 추천을 선택하면 목표 거리를 계산한다.

```js
targetDistanceKm = speedKmPerHour * (targetMinutes / 60);
```

거리 기준 추천을 선택하면 예상 시간을 계산한다.

```js
estimatedMinutes = (targetDistanceKm / speedKmPerHour) * 60;
```

예상 계산 예시는 아래와 같다.

| 조건      | 계산 결과           |
| --------- | ------------------- |
| 15분 걷기 | 예상 거리 약 1.0km  |
| 15분 조깅 | 예상 거리 약 1.75km |
| 15분 러닝 | 예상 거리 약 2.25km |
| 3km 걷기  | 예상 시간 약 45분   |
| 3km 조깅  | 예상 시간 약 26분   |
| 3km 러닝  | 예상 시간 약 20분   |

## 6. 상태 설계

현재 `conditions`는 거리, 시간, 운동 유형을 동시에 들고 있다.

```js
conditions = {
  distance: null,
  time: null,
  type: null,
};
```

Step 27에서는 선택 상태와 계산 결과를 분리한다. 실제 파일에서는 기존 `routeMode`, `routeLocation`, `destinationLocation`과 자연스럽게 연결하되, 의미는 아래처럼 유지한다.

```js
recommendationState = {
  routeMode: "roundTrip",
  targetMode: "distance",
  activity: "walk",
  distanceKm: 3,
  minutes: null,
  isCustomTarget: false,
};
```

계산 결과는 별도로 관리하거나 파생값으로 계산한다.

```js
calculatedTarget = {
  targetDistanceKm: 3,
  estimatedMinutes: 45,
  targetMinutes: null,
  activity: "walk",
  speedKmPerHour: 4,
};
```

상태 이름은 코드 적용 시 기존 구조와 충돌을 줄이기 위해 `targetMode`, `activityType`, `targetDistanceKm`, `targetMinutes`처럼 명확한 이름을 우선 사용한다.

## 7. UX 설계

### 7.1 홈 화면 조건 구조

1차 구현의 홈 화면 조건 순서는 아래를 기준으로 한다.

```text
주소 입력
코스 방식
추천 기준
운동 유형
거리 선택 또는 시간 선택
예상 정보
코스 생성
```

거리 기준 선택 시:

```text
추천 기준
[거리 기준] [시간 기준]

운동 유형
[걷기] [조깅] [러닝]

거리 선택
[1km] [2km] [3km] [5km] [직접 설정]

예상 정보
목표 거리: 3km
예상 시간: 걷기 기준 약 45분
허용 범위: 약 2.4km ~ 3.6km
```

시간 기준 선택 시:

```text
추천 기준
[거리 기준] [시간 기준]

운동 유형
[걷기] [조깅] [러닝]

시간 선택
[15분] [30분] [45분] [60분] [직접 설정]

예상 정보
목표 시간: 30분
예상 거리: 걷기 기준 약 2.0km
허용 범위: 약 1.6km ~ 2.4km
```

### 7.2 직접 설정

직접 설정은 모바일에서 복잡하지 않게 아래 범위를 우선 검토한다.

| 기준           | 범위         | 단위  |
| -------------- | ------------ | ----- |
| 거리 직접 설정 | 0.5km ~ 10km | 0.5km |
| 시간 직접 설정 | 5분 ~ 120분  | 5분   |

구현 방식은 기존 CSS와 모바일 레이아웃을 고려해 선택한다.

- 우선안: `input type="range"` 슬라이더와 현재 선택값 텍스트
- 보조안: 숫자 입력 또는 스텝 버튼

### 7.3 안내 문구

선택 영역에는 정확한 보장을 암시하지 않고 "예상" 표현을 사용한다.

```text
목표 거리 3km에 가까운 코스를 추천합니다.
실제 경로는 도로 상황에 따라 약간 달라질 수 있습니다.
```

결과 화면에는 실제 추천 결과와 목표 차이를 표시한다.

```text
목표 거리: 3km
실제 추천 거리: 3.2km
예상 시간: 약 48분
목표와의 차이: 약 +0.2km
```

실패 시에는 아래 문구를 기준으로 한다.

```text
조건에 맞는 코스를 찾지 못했습니다.
현재 주소 주변에서는 선택한 조건에 가까운 경로를 만들기 어렵습니다.
거리 또는 시간을 조금 늘려 다시 시도해 주세요.
```

## 8. 서버 후보 검증 설계

### 8.1 공통 원칙

- 직선거리나 랜덤 지점 반경만으로 최종 추천하지 않는다.
- ORS 응답의 실제 `summary.distance`와 `summary.duration`을 기준으로 검증한다.
- 조건을 만족하는 후보가 여러 개이면 목표 거리와 가장 가까운 후보를 선택한다.
- 조건을 만족하는 후보가 없으면 억지로 추천하지 않는다.
- 1km 목표에서 2km 이상 경로가 추천되는 상황은 막는다.

### 8.2 허용 오차

초기 구현은 거리별 허용 오차를 적용한다.

| 목표 거리 | 허용 오차 |
| --------- | --------- |
| 1km 이하  | ±30%      |
| 3km 이하  | ±20%      |
| 5km 이상  | ±15%      |

직접 설정 값이 3km와 5km 사이인 경우는 1차 구현에서 ±20% 또는 ±15% 중 구현 난이도와 UX를 보고 결정한다. 단순화를 원하면 전체 ±20%로 시작할 수 있지만, 1km 선택 시 2km 이상 추천은 반드시 차단한다.

### 8.3 순환 코스

순환 코스는 목표 거리와 랜덤 지점 반경을 동일하게 보지 않는다. ORS `round_trip.length`는 목표값으로 전달하되, 실제 추천 여부는 전체 경로의 실제 거리로 판단한다.

처리 흐름:

1. 목표 거리와 seed를 바탕으로 ORS round trip 후보를 생성한다.
2. seed를 바꿔 여러 후보를 생성한다.
3. 각 후보의 `summary.distance`를 km로 변환한다.
4. 목표 거리 허용 범위 안에 있는 후보만 통과시킨다.
5. 통과 후보 중 목표 거리와 가장 가까운 후보를 선택한다.
6. 통과 후보가 없으면 실패 응답을 반환한다.

### 8.4 출발-도착 코스

출발-도착 코스는 사용자가 직접 도착지를 고르므로, 목표 거리보다 기본 경로가 길 수 있다. 이 경우 억지로 우회 경유지를 조정해 목표에 맞추지 않는다.

처리 흐름:

1. 출발지와 도착지만 포함한 기본 ORS 경로 후보를 먼저 확인한다.
2. 기본 경로가 목표 허용 범위를 크게 벗어나고 이미 목표보다 길면 실패 안내를 반환한다.
3. 기본 경로가 목표 안에 있거나 목표보다 짧으면 랜덤 경유지 후보를 생성한다.
4. 여러 후보의 실제 `summary.distance`, `summary.duration`을 비교한다.
5. 목표와 가장 가까운 후보를 반환한다.

목표보다 도착지가 먼 경우의 안내 문구:

```text
선택한 도착지는 목표 거리보다 멉니다.
목표 거리: 1km
예상 경로: 2.4km
조건을 변경하거나 다른 도착지를 선택해 주세요.
```

## 9. API 설계 방향

기존 API 엔드포인트는 유지한다.

- `POST /api/routes/address-round-trip`
- `POST /api/routes/address-point-to-point`

요청 body는 기존 `distance`, `time`, `type` 중심에서 목표 모드를 명확히 표현하는 방향으로 확장한다.

```json
{
  "targetMode": "distance",
  "targetDistanceKm": 3,
  "targetMinutes": null,
  "activity": "walk",
  "seed": 42
}
```

하위 호환을 위해 1차 구현에서는 기존 `distance`, `time`, `type` 필드를 함께 보낼 수 있다.

```json
{
  "distance": 3,
  "time": 45,
  "type": "walk",
  "targetMode": "distance",
  "targetDistanceKm": 3,
  "estimatedMinutes": 45
}
```

응답 `meta`에는 목표 검증 정보를 포함한다.

```json
{
  "success": true,
  "data": {},
  "meta": {
    "targetMode": "distance",
    "targetDistanceKm": 3,
    "estimatedMinutes": 45,
    "actualDistanceKm": 3.2,
    "actualMinutes": 48,
    "distanceDeltaKm": 0.2,
    "acceptedToleranceRate": 0.2,
    "candidateCount": 5,
    "retryCount": 2,
    "notice": "목표 거리와 가까운 코스를 찾았습니다."
  }
}
```

## 11. 검증 항목

- 거리 기준 선택 시 시간 선택 UI가 숨겨지거나 비활성화되는지 확인
- 시간 기준 선택 시 거리 선택 UI가 숨겨지거나 비활성화되는지 확인
- 거리 기준 3km + 걷기 선택 시 예상 시간이 약 45분으로 표시되는지 확인
- 시간 기준 15분 + 걷기 선택 시 예상 거리가 약 1km로 표시되는지 확인
- 직접 거리 설정에서 0.5km 단위 조절이 가능한지 확인
- 직접 시간 설정에서 5분 단위 조절이 가능한지 확인
- 순환 코스에서 ORS 실제 전체 거리 기준으로 허용 범위가 적용되는지 확인
- 출발-도착 코스에서 기본 경로가 목표보다 먼 경우 안내 메시지가 표시되는지 확인
- 조건에 맞는 후보가 없을 때 저장 DB 코스 fallback이 반환되지 않는지 확인
- 1km 목표에서 2km 이상 경로가 추천되지 않는지 확인
- 결과 화면에서 목표 거리/시간, 실제 거리/시간, 목표와의 차이가 표시되는지 확인
- 모바일 375px 화면에서 프리셋 칩과 직접 설정 UI가 겹치지 않는지 확인
- 데스크톱 1280px 이상 화면에서 조건 영역이 과도하게 넓어지지 않는지 확인
- `npm.cmd --prefix client run lint`
- `npm.cmd --prefix client run build`
- 수정한 서버 JS 파일에 대해 `node --check <file>`

## 12. 확정 구현 기준

| 항목        | 확정 기준                                                                   |
| ----------- | --------------------------------------------------------------------------- |
| 추천 기준   | `거리 기준`과 `시간 기준`을 분리한다.                                       |
| 운동 유형   | 걷기 4km/h, 조깅 7km/h, 러닝 9km/h 기준으로 계산한다.                       |
| 거리 프리셋 | 1차 구현은 `1km / 2km / 3km / 5km / 직접 설정`을 사용한다.                  |
| 시간 프리셋 | 1차 구현은 `15분 / 30분 / 45분 / 60분 / 직접 설정`을 사용한다.              |
| 직접 설정   | 거리 0.5~10km, 시간 5~120분 범위에서 구현한다.                              |
| 검증 기준   | ORS 실제 `summary.distance`, `summary.duration`을 사용한다.                 |
| 후보 선택   | 허용 범위 안의 후보 중 목표 거리와 가장 가까운 후보를 선택한다.             |
| 실패 처리   | 조건에 맞는 후보가 없으면 실패 안내를 반환한다.                             |
| DB fallback | 생성형 코스 목표 검증 실패 시 저장 DB 코스를 억지로 반환하지 않는다.        |
| 결과 문구   | 정확한 보장이 아니라 `예상 거리`, `예상 시간`, `실제 추천 거리`로 표현한다. |

## 13. 한계와 후속 검토

- ORS 후보를 여러 번 생성하면 응답 시간이 늘 수 있다. 후보 개수는 초기 구현에서 3~5개 수준으로 제한하고 실제 체감 속도를 확인한다.
- ORS API 실패 또는 제한 상황에서는 정확도 개선 로직도 실패할 수 있다.
- 시간 기준은 운동 유형별 평균 속도 기반 예상값이므로 사용자 개인 속도와 다를 수 있다.
- 직접 설정 범위가 넓어질수록 ORS round trip 생성 실패 가능성이 커질 수 있다.
- 운동 유형별 거리 프리셋 분리는 후속 Step에서 검토한다.
- 지도 중심 바텀시트 UI는 현재 홈 화면 구조 변경 폭이 크므로 후속 UX 개선으로 분리한다.
- POI 기반 경유지 선택이나 보행 가능 영역 필터링은 후속 정확도 개선에서 검토한다.
