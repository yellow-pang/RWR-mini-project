> **상태**: 구현 완료  
> **작성일**: 2026.06.03  
> **브랜치**: `feat/step-28-map-first-route-controls`

> **관련 문서**: [step-27-route-target-accuracy.md](../steps/step-27-route-target-accuracy.md) | [pr-27-route-target-accuracy.md](../pr/pr-27-route-target-accuracy.md)

## 1. 작업 배경

Step 27에서는 추천 기준을 `거리 기준`과 `시간 기준`으로 분리하고, 운동 유형별 속도와 ORS 실제 거리 검증을 적용했다. 이로써 추천 결과의 목표 정확도는 좋아졌지만, 홈 화면에는 주소 선택, 코스 방식, 추천 기준, 운동 유형, 거리/시간 프리셋, 직접 설정, 예상 정보, 생성 버튼이 한 화면에 모이게 되었다.

RWR은 조건 입력 자체보다 지도 위에서 코스를 확인하는 경험이 핵심이다. 모바일 화면에서 조건 영역이 길어지면 정작 사용자가 봐야 할 지도 공간이 줄어들고, 추천 결과가 지도에 표시된다는 서비스의 장점도 약해진다.

Step 28에서는 홈 화면을 지도 중심으로 재구성한다. 모바일은 지도 위주 화면과 하단 고정 패널 형태의 바텀시트 UI를 사용하고, 데스크톱은 왼쪽 조건 패널과 오른쪽 지도 구조를 사용한다. 또한 Step 27 후속 항목이었던 운동 유형별 거리 프리셋과 출발지/도착지 바꾸기, 우회 강도 선택을 함께 정리한다.

---

## 2. 목표

- 모바일 홈 화면에서 지도 영역을 화면 대부분에 배치한다.
- 조건 선택 영역은 모바일에서 하단 고정 패널처럼 보이게 한다.
- 데스크톱에서는 왼쪽 조건 패널과 오른쪽 지도의 2단 레이아웃을 사용한다.
- 처음 구현은 드래그 가능한 3단계 바텀시트가 아니라 고정 하단 패널로 제한한다.
- 운동 유형에 따라 거리 기준 프리셋을 다르게 보여준다.
- 시간 기준 프리셋은 Step 27의 공통 프리셋을 유지한다.
- 출발-도착 코스에서 출발지와 도착지를 한 번에 바꾸는 버튼을 제공한다.
- 출발-도착 코스에서 우회 강도를 선택할 수 있게 한다.
- 우회 강도는 1차 구현에서 API 요청에 포함하되, 서버 반영 범위는 기존 랜덤 경유지 로직에 무리 없이 적용 가능한 수준으로 제한한다.
- POI 기반 경유지는 별도 Step으로 분리한다.

## 4. 사용자 흐름

### 4.1 모바일 기본 흐름

1. 사용자가 홈 화면에 진입한다.
2. 화면 상단에는 주소 선택 동작을 빠르게 시작할 수 있는 영역이 보인다.
3. 지도는 화면 대부분을 차지한다.
4. 하단에는 `오늘의 랜덤 코스` 조건 패널이 고정되어 보인다.
5. 사용자는 패널에서 코스 방식, 추천 기준, 운동 유형, 거리/시간, 우회 강도를 선택한다.
6. `코스 생성`을 누르면 추천 결과가 생성되고 지도 위에 경로가 표시된다.

### 4.2 데스크톱 기본 흐름

1. 사용자가 홈 화면에 진입한다.
2. 왼쪽에는 조건 패널이 고정 폭으로 보인다.
3. 오른쪽에는 지도 영역이 넓게 보인다.
4. 조건을 바꾸어도 지도 영역이 크게 유지된다.
5. 생성 결과가 있으면 오른쪽 지도에 경로를 표시하고, 필요한 요약 정보는 조건 패널 또는 결과 화면에서 확인한다.

### 4.3 출발-도착 바꾸기

1. 사용자가 `출발-도착 코스`를 선택한다.
2. 출발지와 도착지를 모두 선택한다.
3. 사용자가 바꾸기 버튼을 누른다.
4. 기존 출발지는 도착지로, 기존 도착지는 출발지로 교환된다.
5. 현재 위치 사용 버튼은 계속 출발지 보조 기능으로만 동작한다.

### 4.4 우회 강도 선택

1. 사용자가 `출발-도착 코스`를 선택한다.
2. 우회 강도 선택 영역이 표시된다.
3. 사용자는 `가볍게`, `적당히`, `많이` 중 하나를 고른다.
4. 서버는 선택값에 맞춰 랜덤 경유지 수와 경유지 흩어짐 정도를 조정한다.
5. 도착지가 목표 거리보다 이미 멀면 기존 Step 27 정책대로 무리하게 우회하지 않고 실패 또는 안내를 반환한다.

## 5. UX 설계

### 5.1 모바일 레이아웃

모바일은 아래 구조를 기준으로 한다.

```text
┌────────────────────┐
│ 출발 주소 / 주소 찾기 │
├────────────────────┤
│                    │
│        지도          │
│                    │
│  추천 경로 또는 위치  │
│                    │
├────────────────────┤
│ ━━━━━              │
│ 오늘의 랜덤 코스      │
│ [순환] [출발/도착]    │
│ [거리 기준] [시간 기준]│
│ [걷기] [조깅] [러닝]  │
│ [프리셋 칩들]         │
│ 예상 정보             │
│ [코스 생성]           │
└────────────────────┘
```

1차 구현에서는 바텀시트를 드래그로 열고 닫지 않는다. 하단 고정 패널에 `max-height`와 내부 스크롤을 적용해 모바일 375px에서도 화면이 깨지지 않게 한다.

### 5.2 데스크톱 레이아웃

데스크톱은 아래 구조를 기준으로 한다.

```text
┌──────────────┬────────────────────┐
│ 조건 설정     │        지도          │
│ 주소 선택     │                    │
│ 코스 방식     │                    │
│ 추천 기준     │                    │
│ 운동 유형     │                    │
│ 거리/시간     │                    │
│ 우회 강도     │                    │
│ 코스 생성     │                    │
└──────────────┴────────────────────┘
```

조건 패널은 과도하게 넓어지지 않게 고정 또는 최대 폭을 둔다. 지도 영역은 남은 공간을 채우도록 한다.

### 5.3 운동 유형별 거리 프리셋

거리 기준 선택 시 운동 유형에 따라 다른 프리셋을 보여준다.

| 운동 유형 | 거리 프리셋                   |
| --------- | ----------------------------- |
| 걷기      | `1km / 2km / 3km / 직접 설정` |
| 조깅      | `2km / 3km / 5km / 직접 설정` |
| 러닝      | `3km / 5km / 7km / 직접 설정` |

`10km`는 러닝 사용자에게 자연스러운 값이지만, ORS 후보 생성 실패율과 응답 시간을 먼저 확인할 필요가 있다. 1차 구현에서는 `7km`까지만 노출하고, 직접 설정으로 더 긴 값을 선택할 수 있게 한다.

시간 기준은 Step 27의 공통 프리셋을 유지한다.

```text
15분 / 30분 / 45분 / 60분 / 직접 설정
```

운동 유형을 바꿨을 때 현재 선택된 거리값이 새 프리셋에 없더라도 직접 설정 값으로 유지할지, 기본값으로 보정할지는 구현 시 기존 상태 흐름을 보고 결정한다. 사용자 혼동을 줄이려면 기본 프리셋 값으로 보정하는 방식을 우선 검토한다.

### 5.4 우회 강도

우회 강도는 출발-도착 코스에서만 노출한다.

| 표시명 | 내부 값  | 의미                                     |
| ------ | -------- | ---------------------------------------- |
| 가볍게 | `light`  | 기본 경로에 가까운 짧은 우회             |
| 적당히 | `medium` | 현재 랜덤 산책형 경로와 비슷한 우회      |
| 많이   | `strong` | 목표 거리 안에서 더 돌아가는 경유지 생성 |

순환 코스는 이미 ORS round trip 방식이므로 이번 Step에서는 우회 강도 선택을 숨긴다.

## 6. 상태 설계

기존 전역 상태의 `routeMode`, `routeLocation`, `destinationLocation`, `targetMode`, `activityType`, `targetDistanceKm`, `targetMinutes` 흐름을 유지한다.

Step 28에서는 아래 상태를 추가하거나 기존 조건 상태에 병합한다.

```js
detourLevel = "medium";
```

거리 프리셋은 상태로 중복 저장하지 않고, `activityType`과 `targetMode`에서 파생한다.

```js
distancePresets = getDistancePresetsByActivity(activityType);
```

출발지/도착지 바꾸기는 별도 데이터 모델을 만들지 않고 기존 위치 객체를 교환한다.

```js
swapRouteEndpoints() {
  routeLocation <-> destinationLocation;
}
```

## 7. API 설계 방향

기존 엔드포인트는 유지한다.

- `POST /api/routes/address-round-trip`
- `POST /api/routes/address-point-to-point`

출발-도착 코스 요청에만 `detourLevel`을 추가한다.

```json
{
  "startAddress": "서울 성동구 왕십리로 63",
  "startLatitude": 37.5446,
  "startLongitude": 127.0374,
  "endAddress": "서울 성동구 ...",
  "endLatitude": 37.55,
  "endLongitude": 127.04,
  "targetMode": "distance",
  "targetDistanceKm": 3,
  "targetMinutes": null,
  "estimatedMinutes": 45,
  "type": "walk",
  "detourLevel": "medium",
  "seed": 42
}
```

응답 형식은 Step 27의 `targetSummary`와 기존 `meta.notice` 구조를 유지한다. 필요하면 `meta.detourLevel`을 포함해 실제 적용된 우회 강도를 확인할 수 있게 한다.

```json
{
  "success": true,
  "data": {},
  "meta": {
    "usedFallback": false,
    "detourLevel": "medium",
    "notice": "목표 거리와 가까운 출발-도착 코스를 찾았습니다."
  }
}
```

## 8. 서버 우회 강도 반영 방향

우회 강도는 출발-도착 랜덤 경유지 생성에만 적용한다.

### 8.1 경유지 개수

| 우회 강도 | 기본 경유지 수 방향                             |
| --------- | ----------------------------------------------- |
| `light`   | 현재 거리 조건 기준보다 1개 줄이거나 최소 0~1개 |
| `medium`  | Step 26/27의 기존 기준 유지                     |
| `strong`  | 목표 거리와 기본 경로 차이가 충분할 때 1개 추가 |

### 8.2 경유지 offset

출발지와 도착지 사이의 직선 벡터에 수직 방향 offset을 줄 때, 우회 강도에 따라 offset 범위를 조절한다.

| 우회 강도 | offset 방향 |
| --------- | ----------- |
| `light`   | 작은 offset |
| `medium`  | 기존 offset |
| `strong`  | 큰 offset   |

단, Step 27의 목표 거리 검증을 우선한다. `strong`을 선택해도 실제 경로가 목표 허용 범위를 벗어나면 실패 안내를 반환하거나 더 가까운 후보를 선택한다.

## 10. 검증 항목

- 모바일 375px에서 홈 화면 지도와 하단 조건 패널이 겹치지 않는지 확인
- 모바일에서 조건 패널 내부 스크롤이 자연스럽게 동작하는지 확인
- 데스크톱 1280px 이상에서 왼쪽 조건 패널과 오른쪽 지도 구조가 유지되는지 확인
- 주소 선택 전/후 지도 영역이 빈 화면처럼 보이지 않는지 확인
- 거리 기준에서 걷기 선택 시 `1km / 2km / 3km / 직접 설정`이 표시되는지 확인
- 거리 기준에서 조깅 선택 시 `2km / 3km / 5km / 직접 설정`이 표시되는지 확인
- 거리 기준에서 러닝 선택 시 `3km / 5km / 7km / 직접 설정`이 표시되는지 확인
- 시간 기준에서는 운동 유형과 관계없이 기존 시간 프리셋이 유지되는지 확인
- 출발-도착 코스에서 출발지/도착지 바꾸기 버튼이 두 위치를 정확히 교환하는지 확인
- 출발지만 있거나 도착지만 있는 경우 바꾸기 버튼 동작이 안전하게 처리되는지 확인
- 순환 코스에서는 우회 강도 UI가 숨겨지는지 확인
- 출발-도착 코스에서는 우회 강도 UI가 표시되고 선택 상태가 유지되는지 확인
- point-to-point 요청 body에 `detourLevel`이 포함되는지 확인
- 서버가 `light / medium / strong` 외 값은 검증 오류로 처리하는지 확인
- 목표 거리보다 도착지가 먼 경우 기존 Step 27 안내 정책이 유지되는지 확인
- `npm.cmd --prefix client run lint`
- `npm.cmd --prefix client run build`
- 수정한 서버 JS 파일에 대해 `node --check <file>`

## 12. 한계와 후속 검토

- 고정 하단 패널은 실제 네이티브 앱 같은 드래그 바텀시트 경험까지 제공하지 않는다.
- 홈 화면 지도 영역에 결과 경로와 조건 패널이 함께 보이면 모바일 세로 공간이 빠듯할 수 있다.
- 우회 강도 `strong`은 ORS 후보 실패율을 높일 수 있으므로 실제 API 환경에서 응답 시간을 확인해야 한다.
- 운동 유형별 프리셋은 사용자 평균 체력 기준이 아니므로 향후 개인화 옵션과 충돌할 수 있다.
- POI 기반 경유지는 경로 품질을 더 높일 수 있지만, 카카오 키워드 검색 등 외부 API 사용 정책과 fallback 설계가 필요하다.
- 생성형 코스 저장, 즐겨찾기, 딥링크 복원 정책은 여전히 후속 과제로 남긴다.

## 13. 구현 중 UX 보정

초기 계획은 모바일 홈 화면을 지도 중심 + 하단 고정 조건 패널로 구성하는 방향이었다. 구현 확인 후 RWR의 첫 화면은 지도 탐색보다 코스 추천 조건 입력이 우선되어야 한다고 판단했다.

따라서 최종 구현 기준은 아래로 보정한다.

- 홈 화면은 조건 입력 중심 구조를 유지한다.
- 주소 선택 후에만 작은 위치 확인 지도를 표시한다.
- 추천 결과 화면은 큰 지도 중심으로 구성한다.
- 운동 유형별 거리 프리셋, 우회 강도, 출발지/도착지 바꾸기는 유지한다.
